# lifecycle

Steps 1-2 (investigate and classify, the Brief, the plan, the consumer walk, `hunt` on the plan), the session folder's always-on rules and the skip rule are in `CLAUDE.md`. This skill carries steps 3-10 and the re-entry rules; each step names the file that owns its mechanics.

3. **Implement** in the main thread, then walk the list from step 2 yourself before any review.
4. **Twins, the maintenance editors and `comments` in one message, right after implementing.** They run together because none can lose another's work: `twins` is read-only, and every editor agent here is given `Edit` but **not** `Write`, so each change is a string replacement against the file as it stands rather than a whole-file overwrite. Where two editors share a file but not a region, both edits apply; where an `old_string` does overlap, the `Edit` fails loudly and the agent re-reads and retries - which is why every editor agent's definition must carry that retry rule and must report a still-refused edit as **not applied**. `twins` never edits - apply the sites it reports that hold, with the task's context, before the review, so the widened diff is reviewed once. `comments`: every non-trivial task, over the comments the diff adds or changes - a pre-existing comment stays as it is, and one the diff made false comes back as a report for the main thread to fix. [fill] Project editor agents go here - one per artefact the main thread should never hand-edit (translation files, generated notes, a changelog), each owning its files exclusively. With the Stop gate registered, a check that reads an editor's artefact waits for the next Stop while that agent is still running, so a turn ending mid-write does not block on the half-written state (mechanics in `.claude/hooks/README.md`).
5. **Then apply the twins patches that hold, and re-run only what they invalidated**: an editor whose artefact a patch, a review round or a live-probe fact moved. **Then the last `comments` pass**, once those have returned: over what arrived since its first pass - new files in full, new lines in the others - and skipped when nothing that arrived holds a comment. It runs before the review, so the last `gate` sees the final tree and no comment edit lands after it. When each agent returns, read its report and `git diff --stat`: an agent's "done" is a claim, its hunks are the evidence. A count, site list or `file:line` taken from a report is recounted against the source before it goes into another agent's prompt or a verdict - forwarded as a fact, one miscount is believed by every leg after it. **Adjudication is the `CLAUDE.md` rule (never applied on trust); the verdict goes in the launch's `agents.md` row (in the task file's findings for a launch the ledger cannot show, such as a plan's `hunt` before a context-clearing approval)** - disagreeing is allowed, and a serious one may earn an extra review.
6. **Review: load the `crosscheck` skill and do what it says** - signals, tiers, rounds, what each reviewer is told, what to report. Launch the reviewers in one message and wait: **step 7 runs after the first round returns**, so the app is looked at against a diff that has stopped moving, and a fix a reviewer prescribes is seen in the same visit; a later round's fix that changes what renders gets a re-check of that surface alone. The `crosscheck` live probes are that visit's additions, not a second trip.
7. **Browser check - mandatory whenever the change can be seen there.** Load the `verify-live` skill and run it. "It should work" is not a reason to skip it. **Never start a dev server.** If nothing is listening for this tree, the check is pending: run steps 8-10, say the browser check is pending, and ask the owner to start the server - never mark it unverified and move on. If the browser cannot reach the app - no browser on this machine connected, an error page, the login page - ask the owner to step in, as `verify-live` says; the check is pending the same way until they have. [fill] For a project with no browser UI this step is the command that exercises the change and its output.
8. **Docs drift - once, after the last review round** (and after step 7 where it ran; a pending browser check does not hold this step). The `drift` subagent in `diff` mode over the final diff, including any text `comments` moved into a rule file; its prompt carries the task file's findings with their decisions, which it treats as settled, and the session's facts, each tagged `measured: <command or live request> -> <result>` or `relayed from <agent or file>, not re-checked`, as `crosscheck` section 1 writes them. Check its replacements, apply those for drift the diff created, then read `git diff` of every doc they touched; pre-existing drift goes to the user. A `<SRC_DIR>/` comment the main thread fixes here, after the last `gate` launch, re-arms the Stop gate's review block: the reason goes into the review waiver. A **gap** it proposes (a rule no doc had, for a defect class this task fixed) is checked against its five conditions and applied when they hold; one that fails a condition is dropped with the reason, and one that needs a judgement call goes to the user.
9. **Name what stays unverified - only where it can really fail.** Not a checklist of everything unseen: the one to three things that need the user's data, eyes or judgement **and** have a real chance of being wrong (a value scale nobody measured, a write path never exercised, a layout at another font size), each with what to look at. Beside it, **every decision taken on the user's behalf** during the task - a default picked, a reading chosen between two, a scope drawn - one line each with what it costs if wrong; a decision that stays in the transcript was made in secret.
10. **Verify** - one call, `<CHECK_COMMAND>`, with a Bash or PowerShell `timeout` long enough for the whole chain (up to 600000), awaited to its exit - even when the optional Stop gate (`CLAUDE.md`, Commands) is registered: the gate stops a check that outlives its 110 s budget without counting it as a failure, so it never stands in for this call. **Then end the reply that closes the task with three suggested commit subjects** - the user commits, never this thread. Derive them from the final `git diff`, not from the brief, in the repo's own subject format (read `git log --format='%s' -50`, not a remembered convention), varied by angle rather than wording - what broke, what the user now sees, what the code now does; a diff spanning two unrelated concerns gets subjects per commit.

## Re-entry

**A widened scope re-enters at step 2 and closes before any reviewer is launched** - the user adds a surface mid-task, or `twins` reports sites you decide to take. Grep the new surfaces' consumers, implement them (for twins sites the step-4 agents re-run only as step 5 says), and only then launch step 6.

**A code change made after step 6** - a fix from the browser check, a review-round fix, a late twins patch - re-runs only what it invalidates: an editor agent by the step-5 conditions, launched with the round's reviewers, and the review round as the `crosscheck` skill scopes it. `comments` does not re-run per round: the main thread cuts the comments a round's fix adds, by the comment policy, before that round's `gate`. `drift` runs once, at step 8. When a fix a reviewer prescribed buys no round there, that reason goes into the review waiver.

**A change with nothing under `<SRC_DIR>/` or the config files skips steps 4-7**; code it changes under `.claude/hooks` or `.claude/scripts` gets the review `crosscheck` gives that code, and its step 8 is `drift` alone, after the last round.

## The session folder

Write it as each step closes, never in one pass at the end: an agent's verdict under its `agents.md` row (in the task file for a launch the ledger cannot show) in the turn its report lands, one line per round of changes in `task-<slug>.md` (a tier-0 tweak included), and a re-read of `task-<slug>.md` before the reply that closes a task or a round. What each file holds and the verdict mechanics: `.claude/rules/session-artifacts.md`.
