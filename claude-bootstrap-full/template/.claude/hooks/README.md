# Hooks

Six dependency-free Claude Code hooks (Node 18+, no packages). Every script is tracked; one of the six registrations is not.

| Hook | Event | Registered in | What it does |
| --- | --- | --- | --- |
| `guard.mjs` | `PreToolUse` on `Bash`, `PowerShell`, `Edit`, `Write`, `MultiEdit` | `.claude/settings.json` (tracked - repo policy, like the deny list beside it) | Refuses a tool call CLAUDE.md forbids outright, before it runs |
| `record-activity.mjs` | `SubagentStop` + `PostToolUse` on `Edit` / `Write` / `MultiEdit`, the chrome `navigate` tool and `Agent` | `.claude/settings.json` (tracked) | Appends one file per event to a directory the Stop gate reads: which agents were launched and which finished, which files the model or a subagent edited, whether a browser check happened. An agent launch also appends a row `- HH:MM <type> launched - <description>` to `agents.md` in the session's own `.claude/sessions/` folder, when that session keeps one; the first launch, or the first edit of a file inside that session's folder, that finds no ledger creates it with the rows of the session's earlier launches |
| `gate-registered.mjs` | `SessionStart` (startup, resume, clear) | `.claude/settings.json` (tracked) | Says so when this tree has no Stop gate registered, which is invisible otherwise |
| `compact-pointer.mjs` | `SessionStart` (startup, resume, clear, compact) + `PreCompact` + `PostCompact` | `.claude/settings.json` (tracked) | Names this session's artifact folder. `SessionStart` hands the model the session id prefix and the folder it has, or the name to open one under (`additionalContext`), and on `compact` where to resume from; `PreCompact` and `PostCompact` name the folder to the user (`systemMessage` - the harness rejects `hookSpecificOutput` on `PostCompact`), and on a manual `/compact` `PreCompact` says a handoff needs `/precompact` first. Both compaction events stay silent when the session has no folder |
| `record-loads.mjs` | `InstructionsLoaded` (every load reason) | `.claude/settings.json` (tracked) | One file per `CLAUDE.md` or rule load, which `rules-reach.mjs --loads` replays against its model |
| `verify-gate.mjs` | `SessionStart` (startup, resume, clear, compact) + `Stop` | `.claude/settings.local.json` (gitignored - opt-in, per tree) | Runs the probe check and `<CHECK_COMMAND>` at the end of a turn that changed watched files, blocks once on failure, and blocks once when this session edited `<SRC_DIR>/` with no review |

After changing a hook registration in either settings file, start a new session: a running one is not guaranteed to pick it up.

The hooks read payload fields Claude Code does not promise to keep (`session_id`, `agent_id`, `agent_type`, the tool names `Agent` and `mcp__claude-in-chrome__navigate`). A renamed field fails silently, so an agent launch that leaves no row in the session's `agents.md` means a field moved - check the payload before trusting the Stop gate or the probe fence.

**No hook picks up another session's handoff.** Several sessions can run in the same tree at once, and a handoff belongs to one task, not to whoever starts next. The handoff lives in the session's own folder under `.claude/sessions/` and is handed over by hand - the `precompact` skill ends by printing the sentence to open the next session with. Do not add such a hook. `compact-pointer.mjs` is not that hook: it names only the folder of the session it fires in, and never reads another one.

## Facts about the hook protocol this layer relies on

- A hook reads one JSON payload on stdin: `hook_event_name`, `session_id`, `cwd`, plus `tool_name` / `tool_input` (and `tool_response` after the call) for a tool event, `source` for `SessionStart`, `trigger` (`manual` or `auto`) for `PreCompact`, `stop_hook_active` for `Stop`. `CLAUDE_PROJECT_DIR` is set in every hook's environment, and `${CLAUDE_PROJECT_DIR}` in a registered command resolves per tree, so a worktree needs its own `settings.local.json` for the personal gate.
- `PreToolUse`: exit 2 with the reason on stderr blocks the call and shows the reason to the model; exit 0 allows it.
- `PostToolUse`: fires after the call, for MCP tools too - the matcher is a regex over the tool name (`mcp__<server>__<tool>`). A launch is tool name `Agent` with `tool_input.subagent_type`, and its `tool_response.agentId` is the `agent_id` that agent's `SubagentStop` carries (measured). A subagent's own tool call carries the **parent** session's `session_id` plus its `agent_id` and `agent_type` (measured).
- `SubagentStop`: carries `agent_type`, `agent_id` and the **parent** session's `session_id` (measured). It fires **repeatedly while an agent works**, roughly every 30 seconds, with an empty `agent_type` and the agent's progress line (measured); only the final event names the agent, so anything that counts agent runs drops the empty ones.
- `SessionStart`: `source` is `startup`, `resume`, `clear` or `compact`; stdout JSON `{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"..."}}` injects text into the session's context. A `startup` can keep a session id that already has state - the id survives a restart (measured).
- `Stop`: stdout JSON `{"decision":"block","reason":"..."}` makes the model continue with the reason; `systemMessage` reaches the user only, never the model. There is no third channel - a Stop hook cannot tell the model anything without blocking. `stop_hook_active: true` means the Stop already fired once for this turn - never block again then, or the session loops. A hook still running at its registered `timeout` is killed and writes nothing.
- `PreCompact` / `PostCompact`: `systemMessage` reaches the user. `PostCompact` rejects `hookSpecificOutput` (measured at a real `/compact`), so `compact-pointer.mjs` sends `systemMessage` alone on both and hands the model its pointer through the `SessionStart` whose `source` is `compact`.

## guard.mjs - the PreToolUse guard

Deterministic, milliseconds, no state. Exit 2 with the reason on stderr blocks the call; exit 0 allows it; input it cannot parse is allowed (the deny list in `settings.json` and the rules still stand behind it). It is a best-effort net for a well-meaning model, not a security boundary.

- **Git.** Every `git` occurrence is judged wherever it sits - behind `git -C` or `-c`, inside `$(...)` or backticks, after `xargs` or `cmd /c`, as `git.exe` or a quoted path to the binary, and inside an interpreter one-liner or an argv array (`["git", "stash"]`, escaped quotes included). Refused: the verbs in `GIT_WRITE_VERBS`, the writing subcommands in `GIT_WRITE_SUBCOMMANDS`, `apply` without `--check` / `--stat` / `--numstat` / `--summary`, `merge-file` without `-p` / `--stdout`, a `config` write, `symbolic-ref` with two operands, and `branch` with a delete, move, copy, force or upstream flag. `stash` is judged by an allow list instead: only `git stash list` and `git stash show` pass, since a bare `git stash -m <msg>` pushes and its first non-flag token is the message; the `settings.json` deny entries name the same writing forms (bare `git stash`, `git stash -...` and each writing subcommand). `git tag --list` stays refused by design. A text search (`grep`, `rg`, `findstr`, `Select-String`) and a read verb's quoted argument (`git log -S "git add"`) are text, unless the segment runs a `$(...)`.
- **`gh`** is refused when it creates, merges, edits, closes, reopens, locks, transfers or deletes anything, and for `gh api` with a non-GET method or, with none given, a field flag - except a `graphql` query with no `mutation`.
- **Interpreters and nested shells.** A one-liner (`node -e` / `-p`, `python -c`, `py -c`, `pwsh -Command`, `iex`) is refused when a write API in it (`writeFileSync`, `rmSync`, `open` with a write mode; `copyFileSync` / `renameSync` / `shutil.copy` on the destination, a rename on its source too) names anything but a literal scratch path - a computed path cannot be proven scratch. A `.NET` write (`[IO.File]::WriteAllText`, `Copy` / `Move` / `Replace`, `[IO.Directory]::Delete`) is judged the same in any command. The string body of `bash -c`, `sh -c`, `cmd /c`, `pwsh -Command` and `iex`, every `$(...)` outside single quotes and every bash backtick pair is checked again as a command line, read with the outer tool's own quoting.
- **Working directory.** `cd`, `chdir`, `pushd`, `popd`, `Set-Location`, `sl`, `Push-Location` and `Pop-Location` are refused at the head of any top-level command, because the cwd persists across calls and into another worktree. Only a Bash subshell - `( ... )`, `$(...)`, a `bash -c` body - may change it; PowerShell has no subshell, so its parentheses and script blocks do not count, and its `cd..` / `cd\` shortcuts are refused too. This and every other command check judge each command twice - as written and with its shell comments blanked, a `bash -c` / `pwsh -Command` body likewise with its own shell - and refuse if either view does, so an apostrophe in `# it's` cannot open a quote that hides the lines after it, while the blanked view can only add a refusal, never lift one. Blanking takes a `#` that is a whole word (after unescaped whitespace or `;&|`, outside `${...}`) to the line end or, inside a backtick body, to its closing backtick, and PowerShell's `<# ... #>` only at a word start.
- **Movers.** `cp`, `mv`, `install`, `dd`, `truncate`, `patch`, `shred`, `rsync`, `robocopy`, `xcopy`, `ed`, `ex`, `rm`, `tee`, `unlink`, cmd's `copy`, `move`, `del`, `erase`, `rd` and `rmdir`, the PowerShell `*-Item` cmdlets and their aliases, `Clear-Content` and its alias `clc`, `Tee-Object`, and the downloaders' output flags (`curl -o`, `wget -O`, `-OutFile`) are judged at command position, after leading keywords, assignments, `$null =`, `[void]`, wrappers and an unquoted `cmd /c` are stripped, with commands split at `;`, `|`, `&`, newlines, parentheses and braces outside quotes. A mover is refused when a target is not provably scratch or outside the project (a relative path never is), when a target is a variable the guard cannot resolve (only the scratch variables under Shell writes resolve), or, unless it is `tee`, `Tee-Object` or a downloader, when it has no target. A PowerShell parameter's value is not a path (`-ErrorAction`, `-ItemType`) while `-Path` / `-Destination` are, and a copier's only write is its destination. A comma-joined target (`Remove-Item a,b`) is split and every part judged on its own. `find ... -delete` / `-exec rm` is refused unless every root is scratch, and a mover behind `xargs` always.
- **Inside the project** `MOVER_EXEMPT` at the top of the script passes any mover: anything under `node_modules`, judged after `..` is resolved, and the compile probe `<SRC_DIR>/__hunt_probe*.ts`, which a review agent is required to delete and has no other way to; a project's own exemptions go into `MOVER_EXEMPT`. No other copy or move into the project passes, whatever its flags.
- **The delete grant.** A delete (`rm` / `del` / `Remove-Item` / `unlink`) of a file the change itself orphaned passes with no recursive flag (`-r`, `-R`, `-rf`, PowerShell `-Recurse` or any `-Re` prefix, cmd `/s` or `//s`), never a glob, never a `del` of a directory (it empties it), and **one project path per call**, counted across a chain (`rm a; rm b` is two) - the compile probe counts toward that cap, a path under `node_modules` does not - and never on a path matching `PROTECTED_PATHS`, `.git`, `.claude/hooks/**`, `.claude/settings*.json` or a session's `.claude/sessions/*/agents.md` (a delete wipes the verdicts, and the hook rebuilds only the rows), each judged after `..` is resolved.
- **Shell writes.** Refused when the command edits a file in place (`sed -i`, `perl -i`, `awk -i inplace`, `Set-Content` / `Add-Content` / `Out-File`, `npx prettier --write` / `-w`, `npx eslint --fix`, `npm run lint -- --fix`) - with no scratch exemption, since the target of an in-place edit cannot be told from the rest of the command - or redirects into a file (`>`, `>>`, `2>`, `>|`, `>&`, `&>`, a quoted target too; `2>&1` names no file, and `tee` is a mover) whose target is not provably scratch: `/dev/null`, `$null`, `NUL`, an absolute path outside the project (an ancestor of it, or a glob in one, counts as inside; a `\\?\` prefix is ignored), a `~/` path containing `/tmp/`, `Temp` or `scratchpad`, or a variable naming one (`$S`, `$TMP`, `$TEMP`, `$SCRATCH`, `$TMPDIR`, `$M`, `$env:temp` / `$env:tmp`, `%temp%` / `%tmp%`). A scratch variable is read as written; any other path is judged after `..` is resolved, and `$PWD`, `%CD%` or `$(pwd)` name the project, so `./tmp/x` is refused like any other relative path or unknown variable - repo files are changed with `Edit` / `Write`. Every other quoted span is data, so a `>` inside a search pattern is not a redirect; a heredoc body is not quoted, so one that mentions a banned form or a `>` is refused too - notes and scripts go through `Write`.
- **`Edit` / `Write` / `MultiEdit`**: refused for a path matching `PROTECTED_PATHS` - regex sources at the top of the script, filled by `apply.mjs` from `<GENERATED_PATHS>` and tested against the tool's `file_path` with every backslash turned into `/` (an empty list protects nothing); and, for any file inside the project, when a written **line** contains a dash character - em (U+2014), en (U+2013), figure (U+2012), horizontal bar (U+2015), non-breaking hyphen (U+2011), minus (U+2212) or fullwidth (U+FF0D). The one exception is a line that spells the punctuation rule itself (contains "plain hyphen"), and it is per line rather than per payload, so one exempt sentence cannot carry a whole file's dashes past the check. Files outside the project (memory, scratchpad) are not dash-checked. A `.claude/sessions/*/agents.md` is refused to `Write` whether it exists or not, and to `Edit` / `MultiEdit` while it does not exist: `record-activity.mjs` creates and keeps that ledger, a `Write` over it would wipe its rows, and any tool creating it first would stop the backfill of earlier launches, so a verdict goes in with `Edit` once the hook has made it. Delete the `DASH` check together with the Punctuation section of CLAUDE.md if the project does not want the rule.
- **The probe fence.** When the payload names the agent (`agent_type` `hunt` or `integration`, the `PROBE_AGENTS` set), an `Edit` / `Write` or a mover target inside the project is refused for anything but `<SRC_DIR>/__hunt_probe*.ts` - `node_modules` included. A payload without `agent_type` fails open - the agent's prompt still carries the rule.

The deny list in `settings.json` stays as the first backstop: a deny outranks every allow at every scope, and it needs no script to run. It matches the raw command string, so it catches fewer shapes than the guard does - keep both.

**Known gaps.** A bypass nobody would type by accident is recorded here, not closed with more guard code; a realistic slip, or a retry after a refusal, is a defect to fix.

- Refused though harmless (fail-closed): what the as-written view makes of a comment - a quoted string after a `# it's` comment read as a command, trailing comment words read as arguments (`rm <SRC_DIR>/a.ts # orphaned` counts two paths, `cp a b # backup`, `ls # then git add`), a `;`, `|` or `&` in a comment before a `cd` word; a `cd` line inside a heredoc body, behind an unquoted `cmd /c`, after a `;` in a backtick body, after a `case` pattern's `)` inside a subshell, or after a line continuation, a PowerShell hashtable key named `cd`, and `echo x | cd`; a mover target whose own name holds a comma; one path spelled relative and absolute in one call (two deletes); a copy or `find -maxdepth 1 -delete` into an ancestor directory of the project, and a glob or bracketed name directly under one; a `\\?\UNC\` path; search text holding `bash -c '...'` or `sh -c`; `[[ "$a" > "b" ]]`; a heredoc whose body mentions a banned form; `echo '$(git commit)'`; `printf` / `echo` text naming a git write verb; a `node -e` / `python -c` one-liner whose code quotes a git write verb as text.
- Passes though it writes: a `Write` of an `agents.md` spelled with a trailing dot or space, an 8.3 short name or a `\\?\` prefix, and a delete of one spelled through `%CD%` or `~+`; a `cd` behind `eval`, `builtin`, a backslash or quotes (`\cd`, `"cd"`), PowerShell's `iex "cd ..."` or a module-qualified `Set-Location`; `git stash list --output=<path>` and `git stash show --output=<path>`; an escaped apostrophe in ANSI-C `$'...'` quoting, a `${` inside a heredoc body, a PowerShell here-string that holds a `"`, and a doubled PowerShell backtick before `#`; a command after a heredoc or PowerShell here-string whose body holds an odd number of apostrophes counted both with and without the ones after a `#` word; a comment glued to `(` or `$(` (`(# it's`), or behind an escaped backslash or a line continuation, whose apostrophe hides the lines after it; a `cd` after an escaped or heredoc `(` left unbalanced; a brace list that names two deletes in one token (`rm <root>{/a.ts,/b.ts}`); numeric `open` flags; `pathlib` writes; `case` patterns inside `$(...)`; `timeout` / `env -S` combinations beyond the common forms; a deliberate `--noEmit false` under the `npx tsc` allow entry; a git alias defined with `-c alias.` (`git -c alias.x=commit x`); a verb assembled by string concatenation for `Invoke-Expression`; a scratch variable climbing out with `..` (`$TMP/../../<SRC_DIR>`); a path spelled with a trailing dot, an 8.3 short name, the `\\.\` device prefix or an admin share; a bash brace range or list that the split at braces hides (`rm -rf /d/code/my-ap{o..q}`); an in-tree marker path behind a cwd spelling the check does not rewrite (`$PWD.Path/tmp/x`); `git -C ${ROOT} commit` (the braces split `-C` from its value); a verb assembled inside a one-liner (`'git ' + 'commit'`, `` `git ${v}` ``); git from a `perl -e` one-liner whose first git call is a read; `& git @('add','-A')` and `Start-Process git -ArgumentList @(...)`; `-i` after `sed`'s script (`sed 's,a,b,' -i f`) or after a flag holding a comma (`--expression=s,a,b,`, `perl -Mx=a,b -pi`).

**Self-test** after any change to the regexes, from the project root:

```bash
node .claude/hooks/tests/guard-test.mjs
node .claude/hooks/tests/guard-shell-test.mjs
```

Every line must read `ok`; the tests set `CLAUDE_PROJECT_DIR` themselves. The payloads are built in JavaScript on purpose - a Windows path or a dash typed into a shell argument gets mangled before the guard sees it. Add a case per `PROTECTED_PATHS` pattern (the two commented lines in `guard-test.mjs`).

## record-activity.mjs - what actually happened this turn

Append-only, one file per event, under `os.tmpdir()/claude-verify-gate/events-<hash of the repo root>/`, where the root is `CLAUDE_PROJECT_DIR` - the key the gate reads. It never reads a record back and never touches the gate's state file: the lifecycle launches several agents in one message, so a read-modify-write here would lose records, and a write into the gate's single state object would destroy the baseline it hashes.

Every record carries the writer's session id and a timestamp. Four kinds:

- `launch` - `PostToolUse` on `Agent`: the `subagent_type` (`general-purpose` when none is named), the `agentId` from the call's result, and the launch description.
- `agent` - the final `SubagentStop`: `agent_type` and `agent_id`. The intermediate events, with an empty `agent_type`, are not recorded.
- `edit` - `PostToolUse` on `Edit` / `Write` / `MultiEdit`: the repo-relative path and the tool, plus `agentId` and `agentType` when a subagent wrote it. A path outside the root, another drive included, is not recorded.
- `browser` - `PostToolUse` on `mcp__claude-in-chrome__navigate` to a URL containing `<DEV_BASE_PATH>`, with the `__tree` marker route excluded, because proving the machine is not checking the app. The other chrome tools name no URL and record nothing.

Records older than 48 hours are pruned whenever a launch or a finish is recorded, so a session resumed the next day still finds its own. A launch also appends its row to `agents.md` in the session's folder (`.claude/sessions/*-<first 8 of the session id>/`) when that folder exists - it never creates the folder. The first launch, or the first edit of a file inside that folder, that finds no ledger waits 250 ms for records still being written, then links a complete file into place (a link fails when another hook got there first, so parallel hooks never write it twice) with the rows of the session's earlier launch records, read before the link so no launch is listed twice; a launch whose hook stalls past that wait loses its row, and on a filesystem without hard links the fallback exclusive write can lose one appended in the same instant. Each row carries the description on one line, cut at 80 characters, and every dash character the guard refuses, plus U+2010, turned into a hyphen: a verdict `Edit` anchored on the row would fail otherwise.

Registered in the tracked `settings.json`, so it runs for everyone. Only the personal Stop gate reads it, which is why `gate-registered.mjs` exists: a tree that records everything and reads nothing looks exactly like a working one.

## gate-registered.mjs - the gate that is not there

Reads `.claude/settings.local.json` at session start and, when the file is missing or unreadable or no `Stop` hook in it names `verify-gate.mjs`, injects a line telling the model to run the check command by hand and to tell the owner the gate is off. It reports and never blocks. `settings.local.json` is gitignored and `git worktree add` does not carry it, so without this hook a second tree can run for weeks with no verification and nothing says so.

## record-loads.mjs - the load log

Observe-only: the harness does not await `InstructionsLoaded`, it cannot block, and the hook never reports. Each load of a `CLAUDE.md` or a rule - at session start, on a matching Read, after a compaction, in the main thread or a subagent - becomes one file in `claude-verify-gate/loads-<16 hex of the repo root>/` under `%LOCALAPPDATA%` (or `$XDG_CACHE_HOME`, or `~/.cache`): the payload whole, minus `transcript_path`, plus an ISO `at`. A user cache, not `os.tmpdir()` like the event records, because a temp cleaner would empty a log that has to span two weeks. Records older than 15 days are pruned at session start. `node .claude/scripts/rules-reach.mjs --loads [session id prefix]` replays the log, building the same key from its own location; `.claude/rules/rules-reach.md` says what it checks.

The payload is kept whole because its fields are not documented as shipped. Measured on Claude Code 2.1.283: `session_id`, `cwd`, `hook_event_name`, `file_path`, `memory_type` and `load_reason`; on a load a Read triggered, also `trigger_file_path` and `prompt_id`, plus `globs` (the rule's whole list, braces expanded, a trailing `/**` stripped - not the glob that matched) on a rule load; an interactive session adds `scratchpad_dir`. **There is no `agent_id` or `agent_type`**, not even on a subagent's load: a load is attributed by its trigger path and its time only.

## verify-gate.mjs - the optional Stop gate

Runs the probe check, then `CHECK_COMMAND` (the one verification call from CLAUDE.md, run through the shell), and blocks the turn once with the failing output. The always-on summary lives in `CLAUDE.md` under `## Commands`; everything below is the detail.

### Enabling it

Copy `settings.local.example.json` to `.claude/settings.local.json` (gitignored) - it also sets `CLAUDE_CODE_MAX_RETRIES` to 15 - or merge this block into the one you have, then start a new session:

```json
"hooks": {
  "SessionStart": [{ "matcher": "startup|resume|clear|compact", "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/verify-gate.mjs\"", "timeout": 30, "statusMessage": "Recording verification baseline" }] }],
  "Stop": [{ "hooks": [{ "type": "command", "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/verify-gate.mjs\"", "timeout": 150, "statusMessage": "Verifying files changed this session" }] }]
}
```

**Register it in every tree you work in.** `${CLAUDE_PROJECT_DIR}` resolves per tree, so the block is copied verbatim into each - but `settings.local.json` is gitignored and `git worktree add` does not carry it, so a new tree has no gate at all until you add it. `gate-registered.mjs` says so at session start.

`fork` is deliberately **absent** from the SessionStart matcher: a fork gets a new `session_id`, so it would write a fresh baseline from the already-modified tree and record every edit the parent made as unchanged. Without it a forked session starts from an empty baseline and re-checks whatever is dirty - erring toward blocking rather than passing.

The checks share one time budget (110 s) below the Stop hook's 150 s timeout. A check with under 5 s of the budget left is not started; a check that runs past it is stopped with its whole process tree (`taskkill /T` on Windows, the process group elsewhere) and reported as timed out. Neither counts as a failure or records a result, so the next Stop runs it. Keep the timeout above the budget: a hook the harness kills writes nothing and leaves its checker running.

### What it compares

The **whole working tree** (`git status`, untracked files included) against a baseline taken at session start, by content hash, so a conversation that edits nothing costs nothing and an edit reverted to the original reads as unchanged. The filter (`WATCHED`) is the source extensions plus `tsconfig*.json` and `package.json`; extend it with anything else the check command reads (a fixture, a translation file), or a session that edits only that file passes in silence. Do not extend it with files no check reads: watching them buys a full check run that can only fail on unrelated tree state. `.claude/rules/*.md` and `rules-reach.fixture.json` are watched for the `rules-reach` check alone - a change to only those never runs the check command.

A `startup` and a `clear` (which starts a new session id) baseline the tree as it stands. A `resume` or `compact` that finds no state file - evicted from the temp directory, or pruned - baselines to **empty**, and so does a `Stop` with no state: baselining the live tree there would record work already done as unchanged and disarm the gate for exactly the work most likely to need it. A `startup` that **does** find state means the session id survived a restart: the baseline stays, but the activity window reopens, since the review obligation of a session that has ended is not one the new session can answer for. Other sessions' state files (under `os.tmpdir()/claude-verify-gate/`) untouched for a week are pruned at session start, never the calling session's own.

The root is `CLAUDE_PROJECT_DIR` (the payload's cwd without it), the same key the recorder uses, so a session whose cwd drifted into another tree still reads its own records.

The **checks** do not attribute a change to whoever made it. Your own IDE edits and a parallel session in the same tree count as changes this session made, so the gate can block a turn over code the agent never touched; when that happens, `git status` is the first thing to read. Deferral follows the same line: a check waits for this session's own writers, whose completion brings this session another turn and so another Stop, and for another session's agent only where the two runs collide on disk (its `gate` running the check command, its probe file) - another session's writer is a parallel edit like any other, and waiting on it could leave this session's last turn unchecked with nothing to bring the next Stop. The `gate` collision keeps that residual: a last turn ending while another session's `gate` runs gets no check run of its own, and the note says so to the user.

**The review is per session.** The event directory is keyed by the repo root and shared by every session in it, but each record carries its writer's session id, and the review block reads only its own: another session's edits, `gate` runs, running agents, browser checks and review waiver arm or quiet nothing here. A subagent's edit arms it like the main thread's, except an edit by an agent in `UNREVIEWED_WRITERS` (`comments` as shipped; add a project's own editor agents there).

### The checks, in order

The first failure blocks; the rest are not run. Each check is **deferred** while an agent that writes the files it reads, or collides with its run, is still running - the check waits for the next Stop instead of failing on a half-finished operation, and a deferred run records no result. The note names an agent of another session as `<type> (another session)`:

| Check | When | Deferred while (this session) | Deferred while (any session) |
| --- | --- | --- | --- |
| 1. `probe` - a `<SRC_DIR>/__hunt_probe*.ts` left behind | such a path is among the changes | - | `hunt`, `integration` |
| 2. `check` - `<CHECK_COMMAND>` | a watched file other than a `.claude/rules/*.md` or the rules-reach fixture changed | any running agent outside the read-only set (`Explore`, `Plan`, `claude-code-guide`, `statusline-setup`, `twins`, `drift`, `hunt`, `integration`), `gate` included - a writer can hold a stranded import mid-edit | `gate`, which runs the check command itself (two builds at once can each answer "up to date" against the other's cache) |
| 3. `rules-reach` - `node .claude/scripts/rules-reach.mjs --check` | a `.claude/rules/*.md`, the script or its fixture changed | - | - |

Each `CHECKS` entry decides from the changed paths whether it runs (`when`) and names the agents it waits for (`deferWhile`: `own` for this session's, `tree` for any session's). A project whose editor agent owns one checker splits that checker out of `CHECK_COMMAND` into its own entry, deferred on that agent, which also lets the block name the check that failed. An entry whose label is a sentence rather than a command carries its own `reason(output)`, so the block does not read "re-run `a compile probe left behind`".

"Running" is counted per instance, not per type. A launch record carries the agent id from the Agent call's result, and the finish carries the same id (measured), so a launch is running until its own finish, or for an hour at most - review legs have run past 24 minutes. A launch record without an id is never running (every Agent result carries one; a `fork`'s is unmeasured). A round that launches two `hunt` legs keeps the probe check deferred until both have finished. One limit: continuing an agent through `SendMessage` records no launch, so nothing is deferred for it.

The probe check comes first deliberately: it is the only check whose message says what the file is, and ahead of the check command no unrelated failure can mask it. Exclude that path from the build and lint configs as well (the compiler's `exclude`, the linter's ignore list), so a probe live while `gate` runs cannot fail the check command - and then have the probe agents compile through a project of their own, because a probe excluded from the repo's project is not compiled by the repo's command either.

### The review block

After the checks pass, one question the checks cannot ask: **was the change reviewed?** The gate blocks one Stop when a file under `<SRC_DIR>/` **that still exists** was edited by this session later than this session's last `gate` **launch** - a gate launched before an edit did not see it, whenever it finished, and a background reviewer outlives the turn that started it; a finish counts only when no launch was recorded. The existence test keeps a file written and deleted inside one turn - a compile probe, a reverted addition - from demanding a review of nothing. It names the files edited after the last `gate` and leaves the tier to the `crosscheck` skill. After a block, further edits of the files it named stay quiet until a `gate` launch or a waiver answers it; an edit of a file the block did not name blocks again. A `/clear` starts a new session id, so the cleared conversation inherits neither the block nor the review it asked for.

Two cases turn the block into a message:

- **The review is still ahead.** An agent of the lifecycle (`LIFECYCLE_AGENTS`: `twins`, `comments`, `gate`, `hunt`, `integration`, `drift`; add a project's own editor agents) of this session is still running, whenever it was launched: `review pending - <types> still running`. `Explore`, `Plan` and similar launches do not count. Nothing is recorded as blocked, so the next Stop after those agents return asks again.
- **The review was deliberately skipped.** Editing under `<SRC_DIR>/` with no `gate` run is a legitimate outcome: the skip rule in `CLAUDE.md`, a main-thread review under "no subagents", a fix a reviewer prescribed and you applied verbatim, a substituted reviewer. The main thread declares it by writing the reason as the body of **`.claude/.gate-waivers/review-<first 8 characters of the session id>`** (with `Write`) - the block names the exact path, and `compact-pointer.mjs` names the prefix at session start - and the same line into the task file, if the session keeps one. The waiver counts only when it is newer than the last edit and not empty, so the next edit re-arms the block with no file to delete. It is the only waiver: it suspends no check, and no file there does. Waivers older than a week are pruned at session start.

A `<SRC_DIR>/` edit newer than this session's last browser record adds a **message, never a block** - only while no lifecycle agent of this session is running, since the browser check comes after the reviewers, and only while a dev server for this tree answers on `<DEV_BASE_PATH>__tree` at a port in `<DEV_PORT_RANGE>`, with a JSON body whose `tree` is this repo's root. With nothing running, the browser check is the owner's to start and the message would fire every turn instead of meaning something.

A Stop that fires while the model is already continuing after a block (`stop_hook_active`) never blocks again: a check failure there is reported to the user and **not recorded**, so the next ordinary Stop re-runs the check and blocks with a reason the model sees.

Keep `.claude/.gate-waivers/` untracked: deny it in `.gitignore`, or rely on a deny-by-default rule for `.claude/`.

### What it does not cover

- **Formatting** - a formatter run at commit time stays the only formatting gate.
- **Any tree but its own** - a session editing files in another worktree passes clean while that tree is broken, and a worktree carrying an older copy of these hooks behaves as that copy says.

### Failure behaviour

It always exits 0. It never blocks twice on the same tree state - a second Stop there reports `still failing (not re-run)` - and degrades to a message instead of blocking when anything inside it throws. Every read that can fail on its own - the event directory, a malformed record, the waiver, the marker route - is caught individually rather than left to the outer catch, because that catch is the one path that reports and does not block; for the same reason a failed state write on the blocking path is swallowed, so the block still happens.
