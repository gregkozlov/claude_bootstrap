# init mode

Turns a freshly installed layer into **this** project's layer: the project sections of `CLAUDE.md` written from facts found in the repo, a path-scoped rule set built or brought up to date and enriched, and the units the layer ships tuned to the project. It runs right after the install (`INSTALL.md` ends by asking for it), and again whenever the owner wants: a second `init` on a filled layer is the normal case, not an error - it takes the same path, correcting what went stale and adding what is missing, never rewriting from scratch.

How it differs from the other modes: `rules` works on the rule set alone, without `CLAUDE.md` and without tuning the units; `deep` audits every file of the layer as it stands. `init` reads the project first and writes the project-specific parts: `CLAUDE.md`, the rules and the unit tuning. It runs the `rules` steps by reference and does not restate them.

Every standing rule of `SKILL.md` holds, and so does its "Record the run". The survey below is deliberately not cheap - this layer saves launches elsewhere, never here, since a rule set built on a thin survey costs every later session. **The whole run reads the repo and nothing else**: it starts no service, applies no migration, reads no secret file, and opens no database but through the project's own check command (I2, I6), run only when what it needs is already up - what the code and the example files cannot answer is a question for the owner (I5).

## I1. Survey

First the current state, in the main thread: `wc -c CLAUDE.md`, `grep -n "\[fill\]" CLAUDE.md`, `grep -rn "\[fill\]" .claude`, the bootstrap note at the top of `CLAUDE.md` (still there, or gone), `ls .claude/rules` (missing or empty means no project rule yet), and the three project lists at the top of `.claude/hooks/backend-guard.mjs` as the install filled them. The answer decides the shape of the run: `CLAUDE.md` sections still `[fill]` are written, filled ones are corrected and completed (I2); no project rule means building the set, existing rules mean updating and enriching them (I3).

Then launch these read-only agents in one message, every one on Sonnet (the standing rule), each told never to edit, never to write a file, never to `cd` (absolute paths, `git -C <tree>`), and never to read an env file, a key or a credentials file, start a service or connect to a database:

- (a) **`Explore`, the toolchain:** the build manifest and the task runner with their scripts and targets (the real check, build, run, generation, lint and format commands - never a lockfile), the CI workflow files (what CI runs is the truest list of checks, and of what a check needs: a database, containers, services), the compiler, type-check and lint configs, and **what the linter and the type checker already enforce** - their rule lists and ignore lists - since a rule that restates an enforced check is dead text. Plus the tests: where they live, how one file or case is run, the fixtures and factories, and the convention the existing tests show for what gets a test.
- (b) **`Explore`, the layout and the request path:** `git ls-files` per top-level folder with counts, every folder that holds source code (a server's code rarely sits under one root: several services, commands beside internals, modules of a multi-module build), the naming and folder conventions visible in the code (three sites each), the shared modules other code imports most (`git grep -l` by import), and the path one request takes from the entry point to the store - routing, authentication and authorization, validation, the business layer, data access, serialization, the error format - with the file where each lives and the sites where the code leaves that path. Plus what is generated - a client, server stubs, protocol output, a lockfile, a compiled schema - with the command that regenerates it.
- (c) **`Explore`, data and configuration:** each store (database, cache, queue, object storage) with what owns it; the schema's source of truth and the migration tool, the folder its files live in, the command that creates a migration and the one that applies it locally, and whether a migration is hand-written or generated; where a transaction begins and ends, and the sites that open one by hand; the background work (jobs, consumers, schedules) and how it is retried; every outside service the code calls, with its timeout and retry settings and the fake or sandbox that stands in for it; where configuration is read, the example file that lists the variables, and how the local environment is told apart from the rest. It reads the example file and the code, never the real env file - so where the local env file points is not something it can find: that is a question for I5.
- (d) **`Explore`, the written knowledge:** `README*`, `CONTRIBUTING*`, `docs/`, ADRs, runbooks, the API description (and whether it is written by hand or generated), `AGENTS.md`, `.cursorrules`, `.github/copilot-instructions.md`, a decisions or won't-fix list, and whatever the install merged from an earlier `CLAUDE.md` (its project facts, its prohibitions); plus the current `CLAUDE.md` and every `.claude/rules/*.md`. It returns the facts, the stated conventions, the deliberate exceptions with their reasons, and every statement that contradicts the code.
- (e) **`general-purpose`, the fix history:** `git log --since=12.months --no-merges -i --grep='^fix' --format='%h %s' --name-only` (widen the `--grep` to the project's own fix-subject convention after a look at `git log --format='%s' -50`, and add the reverts and hotfixes), each commit's diff read with `git show`; it names each defect class, and returns the classes fixed twice, or once in a shared module or a migration, with the commits and the files they touched.

Each prompt names the folders it may read. Write the five answers' substance into the run file before the next step: they are the evidence every later step cites.

## I2. CLAUDE.md

- **Every `[fill]` section is written from I1's facts alone**: what the service is and what calls it, the commands, the tests, the stack and the request path, the source folders (every one, listed - `drift` and the `rules` and `deep` modes read the list from there) and the conventions inside them, data and migrations, configuration and environments, the generated code, the generators named in "Shell and file edits", the architecture facts an agent cannot derive from the code in a minute (the deliberate exceptions, the traps with a history, the "looks like a bug and is not" list), the code-style rules no linter enforces. Not an inventory of folders, not a restatement of a framework's docs, not a rule the linter already enforces.
- **A command goes in only once it was found in the manifest, the task runner or CI.** A check that reads and writes nothing outside the tree (compile, type-check, lint, unit tests) is also run once, and its output is the evidence; one that needs a database, containers or a network is documented with what it needs and run only when that is already up locally - never started by this run. Never run a command that writes tracked files or reaches outside the machine (a generator, a migration, a seed, a deploy, a publish) or starts the service - document it from where it was found, or ask in I5. A check command that fails is written down as the project's pre-existing state, never fixed here.
- **The Tests section states the project's convention, found in the code**: where tests live, the command for one file or case, what a run needs, and when the existing history adds a test with a change. A project with no tests gets one line saying so - the layer invents no policy.
- **Each standing decision a reviewer would otherwise flag** is marked settled and deliberate, with its reason.
- **The two lists of the Reachability bar are fitted to the deployment the project really runs** (I1 c): one that does run several instances or a replica takes those words out of the out-of-scope list; one with no queue or no outside callers drops the lines that name them. Nothing is added to "out of scope" without the owner (I5).
- **Where text lives:** a prohibition that must be known before any file is read (never create X, which tool to pick, a command that must not run) goes into `CLAUDE.md`; a convention, a mechanic or a prohibition about code in certain files is rule text (I3). Keep `CLAUDE.md` under the budget its "Surgical Changes" section states (`wc -c CLAUDE.md`) - the layer's own text leaves the project a few kilobytes, so a section that needs more is a rule, not a longer section.
- **A section already filled is not rewritten**: a statement the code contradicts is corrected, a missing project fact is added, the rest stays in the owner's words.
- A `[fill]` the repo cannot answer becomes a question (I5), never a guess; a section that has nothing to say yet keeps one line saying so.
- When nothing is `[fill]` any more, delete the bootstrap note at the top of `CLAUDE.md`.

## I3. Rules

Read `references/rules.md` "Writing a rule" first, and measure every rule with `git ls-files` per glob, as `SKILL.md` "Measuring a rule" says.

- **No project rule:** run `references/rules.md` R7, handing its candidate agents I1's answers so they do not survey again.
- **Rules already there - update and enrich them, never rebuild:** run `references/rules.md` R1-R5. Every existing rule is checked against the code: stale facts corrected, dead lines removed, `paths:` fitted to the real call sites both ways, a rule whose sections serve different files split. Then **enrich**: the useful project knowledge the rules do not hold yet - conventions the code shows, traps from the fix history (I1 e), the contracts of shared modules (I1 b), and the data rules of I1 (c): how a migration is written here and what makes one safe to deploy, where a transaction may be opened, how an outside call is wrapped.
- **What may become rule text**, on top of R5's five conditions: every statement carries its evidence - three or more real sites, or a fix commit - in the run file; it does not repeat the linter, the type checker or `CLAUDE.md`; and it helps whoever edits the files under its glob. A statement with no evidence is a question for the owner (I5), never a rule.
- Every rule is path-scoped, its globs point at the files that really call what it describes, its reach is measured before and after, and it stays within the per-rule budget `references/rules.md` states.
- **The project's own style and decisions are kept**: the wording of an existing rule, an entry of `references/settled.md`, and anything `CLAUDE.md` marks settled.

## I4. Tune the units

The units the layer ships carry generic defaults that only the project can settle. Write each from I1's facts:

- `.claude/agents/hunt.md` - keep the shape of the attack angles; delete the classes the stack cannot produce (no tenants, no queue, no money), and add one per defect class I1 (e) found fixed twice, each as a concrete check. Its section stays inside the budget it states.
- `layer-refs.mjs` - `PREFIXES`: the project's other top-level folders a doc names by path (the migrations folder, the deploy folder).
- Every other `[fill]` the step-I1 grep found under `.claude/`.
- **The hooks are reported, never edited** (the standing rule). Compare the three project lists of `backend-guard.mjs` and the `PROTECTED_PATHS` of `guard.mjs` with what I1 found - a migration folder outside the frozen list, a secret file the repo's ignore file names and the secret list does not, the project's own deploy, seed and reset commands, a generated folder the guard does not protect - and give the owner the exact entry for each, with the test case that proves it.

## I5. Questions - one round

What the repo could not answer goes to the owner once, after I2-I4, as `AskUserQuestion` calls of at most four questions each. Every question carries a recommendation checked against the code first, as the first option, labelled "(Recommended)". **One question is always asked, since no file the run may read answers it: where the local env file points** - which database and which outside services, whether they are this machine's or shared - and what the agent may run against them. The answer goes into `CLAUDE.md` "Configuration and environments" in the owner's words; the "Local only" rule sends every later session there instead of asking again. Other typical items: a check command when the project has none (propose the task-runner target that would chain the checks; never invent a command), which outside callers depend on the API, whether local development drives a local cluster or a cloud emulator (the hook lets those through only when the command names them), a candidate rule with too little evidence, a contradiction between an old doc and the code, whether a policy the layer ships (never commit, the punctuation rule, the local-only rule) stays. Apply the answers; a question left unanswered keeps its recommended default, marked as assumed in the report.

## I6. Verify, report, stamp

```bash
grep -n "\[fill\]" CLAUDE.md; grep -rn "\[fill\]" .claude          # none left but the ones I5 left open, and the mentions of the marker in maintain-ai-layer's own SKILL.md and init.md
grep -rn "<[A-Z][A-Z_]\{2,\}>" CLAUDE.md .claude                   # no unfilled placeholder
node .claude/skills/maintain-ai-layer/layer-refs.mjs                # every hit explained

```

Plus every rule's reach measured once more by git, and the project's check command, run once when what it needs is up - a failure in a file this run did not touch is the project's own state.

The report, in the user's language: what the survey read; the `CLAUDE.md` sections written and the ones corrected; the rules created, updated, split and deleted, and the knowledge added, each with the evidence it stands on (sites or a commit); the candidates rejected, each with the condition it failed; the units tuned; the questions with their answers or assumed defaults; the numbers before and after (`CLAUDE.md` bytes, rule count and bytes, reach); and what is left to the owner - the hook list entries of I4, a settings change.

Last, write today's date (`YYYY-MM-DD`, the only line) into the gitignored `.claude/.last-maintain` with `Write`: the layer was just checked against the repo, and `upkeep-nudge.mjs` counts the days to the next pass from it.
